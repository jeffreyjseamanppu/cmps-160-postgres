Stored Procedures and Functions with PL/pgSQL

Focus: reusable database logic, parameters, validation, calculations, and testing. Tools: PostgreSQL and pgAdmin 4. Scenario: Wine Store.

Scope: This module covers stored procedures and functions only. Triggers are intentionally excluded. The standalone practice schema below prevents accidental changes to your existing course project.

1. Learning outcomes

  1. Describe how procedures and functions differ and select an appropriate routine for a business problem.
  2. Use CREATE OR REPLACE PROCEDURE, CALL, CREATE OR REPLACE FUNCTION, RETURNS, and SELECT.
  3. Write PL/pgSQL blocks with parameters, local variables, IF, RAISE EXCEPTION, and RETURN.
  4. Build routines that update inventory and return calculated or tabular results.
  5. Test normal cases, invalid inputs, and boundary conditions; document expected and actual results.

6. Guided lab A: your first stored procedure

Business problem: A delivery arrives. Rather than allowing staff to write ad hoc UPDATE statements, define one reusable restocking operation. The procedure checks inputs and confirms the product exists.

CREATE OR REPLACE PROCEDURE module9.restock_wine(
    p_product_id INTEGER,
    p_quantity INTEGER
)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_quantity <= 0 OR p_quantity IS NULL THEN
        RAISE EXCEPTION 'Restock quantity must be positive';
    END IF;

    UPDATE module9.products
    SET stock_quantity = stock_quantity + p_quantity
    WHERE product_id = p_product_id;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Product % not found', p_product_id;
    END IF;
END;
$$;

CALL module9.restock_wine(3, 15);
SELECT product_id, product_name, stock_quantity
FROM module9.products WHERE product_id = 3;

Expected result: Riesling stock changes from 12 to 27. Run CALL module9.restock_wine(3, -2); and CALL module9.restock_wine(999, 2); separately. Both should produce intentional errors. Discuss why rejecting invalid input is useful.

7. Guided lab B: a scalar-returning function

Business problem: The store needs a consistent discount calculation that can be used in reports.

CREATE OR REPLACE FUNCTION module9.discounted_price(
    p_price NUMERIC,
    p_percent NUMERIC
)
RETURNS NUMERIC
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_price IS NULL OR p_percent IS NULL
       OR p_price < 0 OR p_percent < 0 OR p_percent > 100 THEN
        RAISE EXCEPTION 'Invalid price or discount';
    END IF;
    RETURN ROUND(p_price * (1 - p_percent / 100), 2);
END;
$$;

SELECT module9.discounted_price(25.00, 10) AS sale_price;
SELECT product_name, price,
       module9.discounted_price(price, 15) AS sale_price
FROM module9.products ORDER BY product_id;

Expected first result: 22.50. Compare calling a function once with using it across every row of a query. Test discounts of 0%, 100%, and 101%.

8. Guided lab C: a price-update procedure

Business problem: Managers need to change a price without accidentally entering a negative amount or updating an unknown product.

CREATE OR REPLACE PROCEDURE module9.change_wine_price(
    p_product_id INTEGER,
    p_new_price NUMERIC
)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_new_price IS NULL OR p_new_price <= 0 THEN
        RAISE EXCEPTION 'New price must be greater than zero';
    END IF;
    UPDATE module9.products
    SET price = ROUND(p_new_price, 2)
    WHERE product_id = p_product_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'Product % not found', p_product_id;
    END IF;
END;
$$;

CALL module9.change_wine_price(4, 27.50);
SELECT product_name, price FROM module9.products
WHERE product_id = 4;

Think: What is the difference between rejecting a negative price in the procedure and using a CHECK constraint on the table? Why might an application need both?

9. Guided lab D: a function that returns rows

Business problem: The store wants to retrieve all wines at or below a given inventory threshold.

CREATE OR REPLACE FUNCTION module9.low_stock_wines(
    p_threshold INTEGER
)
RETURNS TABLE (
    wine_id INTEGER,
    wine_name TEXT,
    quantity_on_hand INTEGER
)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_threshold IS NULL OR p_threshold < 0 THEN
        RAISE EXCEPTION 'Threshold must be zero or greater';
    END IF;
    RETURN QUERY
    SELECT p.product_id, p.product_name, p.stock_quantity
    FROM module9.products AS p
    WHERE p.stock_quantity <= p_threshold
    ORDER BY p.stock_quantity, p.product_id;
END;
$$;

SELECT * FROM module9.low_stock_wines(10);

With the earlier labs completed, Malbec (8 bottles) should be returned. Explain how RETURNS TABLE and RETURN QUERY differ from returning a single number.

Experience 2 — Debugging clinic

Correct this intentionally broken routine. Identify at least four problems, including syntax and logic errors.

CREATE FUNCTION module9.bad_discount(p_price NUMERIC,
                                     p_percent NUMERIC)
RETURNS NUMERIC
LANGUAGE plpgsql
AS $$
BEGIN
  IF p_percent > 100 THEN
    RAISE NOTICE 'Discount too high';
  END IF;
  RETURN p_price - p_percent;
END;
$$;
SELECT module9.bad_discount(20, 10);

Consider whether a warning is sufficient, whether the formula represents a percentage, and how negative or null values should be handled.

Experience 3 — Pair programming / peer review

Partner A writes a procedure to reduce inventory by a sale quantity without allowing stock to go negative. Partner B writes a function that returns TRUE when a requested quantity is available. Exchange SQL and test each other's code with a valid product, an unknown product, zero quantity, and insufficient stock. Discuss which operation belongs in a procedure and which belongs in a function.

Experience 4 — Mini case study

A wine store has 500 products and wants to apply a 10% promotional discount in reports without changing stored prices. Separately, it receives deliveries that must increase inventory. Write a short design recommendation identifying the best routine for each task and explaining why.

Experience 5 — Knowledge check

  1. Which SQL statement invokes a stored procedure?
  2. Which clause declares a function's result type?
  3. What does NOT FOUND detect after an UPDATE in PL/pgSQL?
  4. Why use parameters instead of hard-coded product IDs?
  5. What is the difference between RETURN and RETURN QUERY?
  6. Why should you test a routine with invalid input?

12. Homework — Wine Store Routine Library (100 points)

Scenario: You are a database developer hired to create reusable SQL routines for a wine retailer. Work in the module9 practice schema or adapt the logic to your own Wine Store database. Write your own routines; the guided lab examples are models, not completed homework submissions.

  1. Procedure A — Sell wine (20 points). Create sell_wine(p_product_id INTEGER, p_quantity INTEGER). Decrease inventory only when the product exists, quantity is positive, and enough stock is available. Raise a meaningful exception otherwise. Prevent stock from going negative even if two sessions attempt sales at the same time (hint: use one conditional UPDATE and check its result).
  2. Procedure B — Percentage price increase (20 points). Create increase_wine_price(p_product_id INTEGER, p_percent NUMERIC). Validate the product and accept percentages from 0 to 100 inclusive. Increase and round the price to two decimal places. Raise an exception for invalid values.
  3. Function A — Sales tax calculator (15 points). Create calculate_total_with_tax(p_subtotal NUMERIC, p_tax_percent NUMERIC), returning a rounded total. Reject negative subtotals and percentages outside 0–100.
  4. Function B — Customer spending (20 points). Create customer_total_spent(p_customer_id INTEGER). Calculate the total historical spend using orders and order_items, including quantity times the order item's recorded unit price. Return zero when the customer has no orders. Do not calculate historical spend using today's product price.
  5. Test plan and evidence (15 points). For each routine, run at least three tests: normal input, a boundary case, and an invalid or missing-data case. Show the SQL call, expected result, actual result or expected exception, and a screenshot from pgAdmin.
  6. Documentation and reflection (10 points). Include a 200–300 word explanation of your design, the difference between procedures and functions, and one debugging challenge you encountered.

Required submission: One module9_routines.sql file containing the four routine definitions and test calls; one PDF or document containing screenshots, a test-results table, and the reflection. Add comments identifying each routine and its parameters. Make your script executable in order after the starter setup.

Bonus (up to 5 points): Create a function that returns the top three wines by historical revenue using RETURNS TABLE and RETURN QUERY. Explain why historical unit_price is used.
