Why Database Design Matters

Before we create tables in PostgreSQL, we need to understand what information should be stored and how that information relates to other data.

A Poorly Designed Spreadsheet

Player Team Team City Coach Position Stadium
T.J. Watt Steelers Pittsburgh Mike Tomlin LB Acrisure Stadium
Aaron Rodgers Steelers Pittsburgh Mike Tomlin QB Acrisure Stadium
DK Metcalf Steelers Pittsburgh Mike Tomlin WR Acrisure Stadium
Class Discussion:

What information is being repeated?

What happens if the team changes coaches?

How many rows would need to be updated?

Key Idea:

A relational database separates information into logical tables and connects those tables through relationships.

Entities and Attributes

What is an Entity?

An entity is a person, place, object, event, or concept that we need to store information about.

Examples in a sports database:

TEAM PLAYER COACH GAME STADIUM

What is an Attribute?

An attribute is a characteristic or property of an entity.

TEAM ------------------ team_id team_name city state
PLAYER ------------------ player_id first_name last_name position jersey_number
Think About It:

If you were building a database for a winery, what entities would you need?

Possible entities:

CUSTOMER WINE ORDER CATEGORY

A WINE entity might contain:

WINE ------------------ wine_id wine_name wine_type vintage price

Primary Keys and Foreign Keys

Primary Key

A primary key uniquely identifies each record in a table.

Bad Primary Key: 
player_name

Two players may have the same name.

Better Design: 
player_id
PLAYER ------------------ player_id PK first_name last_name position

Primary keys should:

  • Be unique.
  • Never be NULL.
  • Identify exactly one row.

Foreign Key

A foreign key connects one table to another table.

TEAM ------------------ team_id PK team_name city PLAYER ------------------ player_id PK first_name last_name position team_id FK

The foreign key team_id tells us which team each player belongs to.

team_id team_name city
1 Steelers Pittsburgh
2 Eagles Philadelphia
player_id first_name last_name team_id
101 T.J. Watt 1
102 Aaron Rodgers 1
103 Jalen Hurts 2

Table Relationships

One-to-One

EMPLOYEE 1 -------- 1 EMPLOYEE_BADGE

One employee has one employee badge.

One-to-Many

TEAM 1 -------- * PLAYER

One team can have many players.

One player belongs to one team.

Rule:

In a one-to-many relationship, the foreign key normally goes on the many side.

Many-to-Many

STUDENT * -------- * COURSE

A student can take many courses.

A course can contain many students.

A direct many-to-many relationship must normally be resolved using another table.

STUDENT | | 1 | * ENROLLMENT * | | 1 | COURSE
ENROLLMENT ------------------ student_id FK course_id FK semester grade

The ENROLLMENT table is often called a:

  • Junction table
  • Bridge table
  • Associative entity

Entity Relationship Diagrams

An Entity Relationship Diagram, or ERD, is a visual blueprint of a database.

TEAM ------------------ PK team_id team_name city 1 | | * PLAYER ------------------ PK player_id first_name last_name position FK team_id

ERDs help us design the database before creating tables in PostgreSQL.

Key Question:

What are the entities, and how are they related?

Winery Database

A winery sells multiple wines. Each wine belongs to a wine category. Customers can place orders. Each order can contain multiple wines, and each wine may appear on many different orders.

Class Question:

What entities do we need?

Possible entities:

CUSTOMER WINE CATEGORY ORDER ORDER_ITEM

Relationships

CATEGORY 1 | * WINE CUSTOMER 1 | * ORDER ORDER 1 | * ORDER_ITEM * | 1 WINE

ORDER_ITEM Table

ORDER_ITEM ------------------ order_item_id PK order_id FK wine_id FK quantity price
Question:

Why can't we simply place wine_id inside the ORDER table?

Because one order can contain multiple wines.

Question:

Why can't we place order_id inside the WINE table?

Because the same wine may appear on thousands of different orders.

Possible Solution

PostgreSQL Example

CREATE TABLE professor (
    professor_id INTEGER PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50),
    email VARCHAR(100),
    department VARCHAR(100)
);

CREATE TABLE student (
    student_id INTEGER PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50),
    email VARCHAR(100),
    major VARCHAR(100)
);

CREATE TABLE course (
    course_id INTEGER PRIMARY KEY,
    course_code VARCHAR(20),
    course_name VARCHAR(100),
    credit_hours INTEGER,
    professor_id INTEGER,
    FOREIGN KEY (professor_id)
        REFERENCES professor(professor_id)
);

CREATE TABLE enrollment (
    enrollment_id INTEGER PRIMARY KEY,
    student_id INTEGER,
    course_id INTEGER,
    semester VARCHAR(30),
    grade VARCHAR(5),
    FOREIGN KEY (student_id)
        REFERENCES student(student_id),
    FOREIGN KEY (course_id)
        REFERENCES course(course_id)
);

Module 2 Summary

Before building a database, always ask:

  1. What information do I need to store?
  2. What are my entities?
  3. What attributes belong to each entity?
  4. What uniquely identifies each record?
  5. How are the entities related?
  6. Where should foreign keys be placed?
  7. Do I need a junction table?
Main Takeaway:

Do not start by creating tables. Start by understanding the data and how the information relates to everything else.

Module 3 - Database Normalization

In Module 2, we learned how to identify entities, attributes, primary keys, foreign keys, and relationships.

In Module 3, we will take the next step and determine whether our database is actually designed correctly.

Big Question:

Just because a database works, does that mean it is designed well?

Database normalization helps organize data to reduce unnecessary duplication, improve data integrity, and make databases easier to maintain.

Module 3 Lecture - Database Normalization

Why Normalize a Database?

Consider the following table used to track university enrollment.

Student ID Student Name Course Professor Professor Office Grade
1001 John Miller CMPS160 Jeff Seaman 401 A
1001 John Miller CMPS360 Jeff Seaman 401 B
1002 Sarah Johnson CMPS160 Jeff Seaman 401 A
1003 Michael Brown CMPS160 Jeff Seaman 401 B
Class Discussion:

What information is being repeated in this table?

What happens if Professor Seaman moves from office 401 to office 405?

Professor information appears repeatedly. If the professor changes offices, multiple records may need to be updated.

Database Anomalies

Update Anomaly

The same information appears in multiple records. Changing the information requires updating multiple rows.

Insertion Anomaly

We may be unable to add information about a new course until a student enrolls in the course.

Deletion Anomaly

Deleting the last student enrolled in a course could accidentally remove the only information we have about that course.

Goal of Normalization:

Store each fact in the appropriate place and reduce unnecessary duplication.

First Normal Form - 1NF

First Normal Form requires each field to contain a single, atomic value and eliminates repeating groups.

Bad Design

student_id student_name courses
1001 John Miller CMPS160, CMPS360, CMPS262
Problem:

The courses column contains multiple values.

Better Design

student_id student_name course
1001 John Miller CMPS160
1001 John Miller CMPS360
1001 John Miller CMPS262

Another 1NF Violation

STUDENT ------------------ student_id student_name course1 course2 course3 course4
Think About It:

What happens when a student takes a fifth course?

Remember 1NF:

One value per field. Eliminate repeating groups.

Second Normal Form - 2NF

A table must first satisfy 1NF.

In Second Normal Form, every non-key attribute must depend on the entire key.

ENROLLMENT -------------------------------- student_id course_id student_name course_name grade

Assume the logical key is: 

(student_id, course_id)

Now consider these dependencies:

student_id → student_name course_id → course_name student_id + course_id → grade

Student name only depends on student_id.

Course name only depends on course_id.

These are examples of partial dependencies.

Normalize the Tables

STUDENT ---------------- student_id PK student_name COURSE ---------------- course_id PK course_name ENROLLMENT ---------------- student_id PK/FK course_id PK/FK grade
Remember 2NF:

Every non-key attribute should depend on the whole key.

Third Normal Form - 3NF

A table must first satisfy 2NF.

In Third Normal Form, non-key attributes should depend on the primary key rather than another non-key attribute.

Problem Design

STUDENT ------------------------ student_id PK student_name major_id major_name department_id department_name

Notice the following dependencies:

major_id → major_name department_id → department_name

Major and department information should not need to be repeated for every student.

Normalized Design

STUDENT ---------------- student_id PK student_name major_id FK MAJOR ---------------- major_id PK major_name department_id FK DEPARTMENT ---------------- department_id PK department_name
Remember 3NF:

Non-key attributes should depend on the key, not another non-key attribute.

Normalization Summary

Normal Form Main Idea
1NF One value per field and no repeating groups.
2NF Every non-key attribute depends on the whole key.
3NF Non-key attributes depend on the key, not other non-key attributes.
Main Takeaway:

Normalization is not simply about creating more tables. It is about determining where each piece of information logically belongs.
